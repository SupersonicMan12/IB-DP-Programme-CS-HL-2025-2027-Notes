## A3.3.1 Outline the differences between data language types within SQL.
- Data language types must include data definition language (DDL) and data manipulation language (DML)
- SQL statements to define data structures or to manipulate data

Data Definition Language (DDL) creates and changes the structure of the database. It is the blueprint of the database / macro commands. Acts on entire **table** or entire **columns.**

`CREATE`: new database

```SQL
CREATE TABLE Item(
	ItemID int NOT NULL PRIMARY KEY ,
	ItemDesc varchar(255),
	ItemCost real,
	ArtistID int,
	FOREIGN KEY(ArtistID) REFERENCES Artist(ArtistID)
);
```

`ALTER`: changes the structure of an object that already exists
```sql
ALTER TABLE Item ADD COLUMN ItemAddress varchar(255);
```

`DROP`: destroys the object
```SQL
DROP TABLE Customer
```

`TRUNCATE`: empties a table while retaining definition

```SQL
TRUNCATE TABLE Customer
```

`RENAME`: changes the name of the database object

```SQL 
RENAME TABLE Customer TO Client
```


Data Manipulation Language (DML) used to access / manipulate the data within the database. They act on **records**, or rows.

Specifics on DML in A3.3.2 (below).

## A3.3.2 Construct queries between two tables in SQL.
- Queries must include joins, relational operators, filtering, pattern matching, and ordering data
- SQL commands: SELECT, DISTINCT, FROM, WHERE, BETWEEN, ORDER BY, GROUP BY, HAVING, ASC, DESC, JOIN, LIKE with % wildcard, AND, OR, NOT (note: Syntax may vary in different database systems)

> [!ai-fix] AI-generated examples — the following minimal examples covering every A3.3.2 command are generated by Claude Fable 5.1.

Tables: `Student(StudentID, Name, House, GradYear)` and `Enrollment(StudentID, Subject, Grade)`. Join on FK = PK: `Enrollment.StudentID = Student.StudentID`.

**Example 1 — every command in one query.** *Per house, count students with grade ≥ 5 in CS/Maths, graduating 2026–27, not Dragon; houses with ≥ 2 such rows only; largest first.*

```sql
SELECT   s.House, COUNT(DISTINCT s.StudentID) AS Students  -- DISTINCT: no duplicates
FROM     Student s
JOIN     Enrollment e ON s.StudentID = e.StudentID        -- JOIN on FK = PK
WHERE    s.GradYear BETWEEN 2026 AND 2027                 -- BETWEEN is inclusive
  AND    (e.Subject LIKE 'CS%' OR e.Subject LIKE 'MATH%') -- LIKE: % = any chars, _ = one char; bracket ORs
  AND    NOT s.House = 'Dragon'                           -- NOT; relational ops: = <> < > <= >=
  AND    e.Grade >= 5
GROUP BY s.House                                          -- one output row per house
HAVING   COUNT(*) >= 2                                    -- filters GROUPS; aggregates go here, not in WHERE
ORDER BY Students DESC, s.House ASC;                      -- ASC is the default
```

**Example 2 — joins.**

```sql
-- INNER JOIN (= JOIN): only rows with a match in BOTH tables
SELECT s.Name, e.Subject, e.Grade
FROM   Student s
INNER JOIN Enrollment e ON s.StudentID = e.StudentID
WHERE  e.Grade = 7
ORDER BY s.Name;

-- LEFT JOIN: keeps ALL left-table rows; no match → NULL. Here: students with no enrollments
SELECT s.Name
FROM   Student s
LEFT JOIN Enrollment e ON s.StudentID = e.StudentID
WHERE  e.StudentID IS NULL;
```

Key points:
- Execution order: `FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY`. So WHERE filters **rows** (no aggregates, no aliases); HAVING filters **groups**; ORDER BY can use aliases.
- Always write `ON FK = PK`. Forgetting it gives a Cartesian product (every row × every row).
- Qualify as `table.column` when a column name exists in both tables.
- Joins repeat the "1" side once per matching "N" row → use `DISTINCT` when listing.
- M:N: chain a second join through the junction table, e.g. `JOIN Class c ON e.ClassID = c.ClassID`.
- Old style `FROM Student s, Enrollment e WHERE s.StudentID = e.StudentID` is also accepted. Syntax varies by DBMS.

## A3.3.3 Explain how SQL can be used to update data in a database.
• Insert new records (INSERT INTO), modify data (UPDATE SET), remove data (DELETE)
• The performance implications of updating data in indexed columns, and how indexes might need to be rebuilt or reorganized following significant data modifications

``` SQL
INSERT INTO Student (StudentID, Name, House) VALUES (9, 'Ivy', 'Orion');
UPDATE Student SET House = 'Phoenix' WHERE StudentID = 9;
DELETE FROM Student WHERE StudentID = 9;
```
- Omitting WHERE on UPDATE/DELETE affects every row!
- FK constraints may block a DELETE

Indexes: an index is a sorted lookup structure that makes SELECT faster, but every INSERT/UPDATE/DELETE on an indexed column must also update the index, thus writes are slower. This is an important **tradeoff** that may be tested.

Additionally, after bulk changes, the index becomes fragmented. It is rebuilt (dropped and recreated) or reorganized (defragmented in place), think memory fragmentation.

## A3.3.5 Describe different database views. (HL only)
• Virtual views and materialized (snapshot) views
• Hiding data complexity, data consistency, independence, performance, query simplification, read-only data or updatable data, security

A **view** is a **saved** `SELECT` query that you can use as if it were a table.

```SQL
CREATE VIEW HouseAverages AS
SELECT House, AVG(Grade) AS Mean From Student s JOIN Enrollment e ON s.StudentID = e.StudentID GROUP BY House;
```
- Virtual View: a stored query that is recomputed every time it is used
- Materialized (snapshot) view: the result is physically stored, a refresh (complete rebuild) is needed upon update
- Seven syllabus benefits:
	- Hiding Complexity (abstracts to `HouseAverages`) — user queries HouseAverages, not a 3-table join
	- Query simplification — reuse the same join once
	- Security — expose only certain columns/rows, e.g. hide salaries
	- Independence — underlying tables can change; the view interface stays the same
	- Consistency — everyone uses the same definition of "average grade"
	- Performance — materialized views precompute expensive results
	- Read-only vs updatable — simple single-page views can be updated through; views with joins are read-only
## A3.3.6 Describe how transactions maintain data integrity in a database. (HL only)
• The role of atomicity, consistency, isolation and durability (ACID) to ensure reliable processing of transactions
• Transaction control language (TCL) commands: BEGIN TRANSACTION, COMMIT, ROLLBACK

```SQL
BEGIN TRANSACTION
UPDATE Account SET Balance = Balance - 100 WHERE AccountID = 1
UPDATE Account SET Balance = Balance + 100 WHERE AccountID = 2
COMMIT;
```

**Transaction** = a group of SQL statements treated as a single unit of work. **ACID**:
- Atomicity — all or nothing: if the second UPDATE fails, the second is undone. Either all are done or all are not
- Consistency — the Db moves from one valid state to another (constraints hold; total money unchanged)
- Isolation — concurrent transactions do not see each other's half-finished work
- Durability — once **committed**, the change survives a crash / power loss
- `BEGIN TRANSACTION` starts; `COMMIT` makes changes permanent; `ROLLBACK`undoes everything since `BEGIN`
