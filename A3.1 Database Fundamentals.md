## A3.1.1 Explain the features, benefits and limitations of a relational database. 
- Features: composite keys, foreign keys, primary keys, relationships, tables 
- Benefits of databases: community support, concurrency control, data consistency, data integrity, data retrieval, reduced data duplication, reduced redundancy, reliable transaction processing, scalability, security features
- Limitations of databases: “big data” scalability issues, design complexity, hierarchical data handling, rigid schema, object-relational impedance mismatch, unstructured data handling

Understand the key terms, then understand "ethical issues":
- **Tables** = core structure of relational database: organized through rows + columns
- Record = row, the information about one entity
- Field = column, one attribute of the entity
- Relational Databases key features:
	- **Primary Key** = unique identifier for each record (row) in a table
	- **Foreign Key** = a column in a table that references the primary key of ANOTHER TABLE
	- **Composite key** = primary key that consists of two or more columns. When a single column is insufficient to identify a record
	- **Relationships**: how tables are connected in a relational database, through primary and foreign keys:
		- Mandatory Relationship. A must be linked to B. The foreign key cannot be null.
			- A book MUST have a library
		- Optional Relationship: may or may not be linked. The foreign key can be null.
			- A book MAY have an borrower
	- **One-to-one**, each record in one table is related to *exactly one* record in another table
	- **One-to-many**, one record in one table is related to multiple records in another table
	- **Many-to-many**, multiple records in one table are related to multiple records in another table
		- Cannot be stored directly: a field holds only one value, so it cannot hold a list of foreign keys
		- Consider **junction tables**: the two foreign keys form a composite primary key, turning M:N into two 1:N

Benefits of Relational Databases:
- **Data consistency**: each fact is stored once, so an update in one place is seen everywhere
- **Data integrity**: constraints (data types, PK, FK) reject invalid data; referential integrity = every FK must match an existing PK
- **Reduced data duplication** and **redundancy**: tables reference each other through foreign keys instead of copying data
- Efficient **data retrieval**: SQL allows complex queries
- **Scalability**: handles growing data and users by upgrading to more powerful hardware
- **Security features**: user authentication, access privileges per table/column, views that hide sensitive data
- **Reliable transaction processing**: ACID transactions are all-or-nothing, so a failure never leaves half-finished changes
- **Concurrency control**: lets many users use the database at the same time without corrupting the data; record locking prevents lost updates
- **Community support**: mature and widely used, with extensive documentation, tools and experienced developers
- Addresses insert, update, delete anomalies: normalized tables let data be added, changed or removed without side effects

Limitations of Relational Databases:
- **"Big data" scalability**: RDB scale vertically (single bigger server) and struggle to spread very large or high velocity datasets across many machines
- **Design Complexity**: getting a correct normalized schema takes skilled design and is difficult to change
- **Rigid Schema**: must be strict relations: structure fixed in advance, every record has the same columns; changing it (ALTER) on a large live database is slow and risky
- **Hierarchical Data Handling** is limited: hierarchies are flattened into a self-referencing FK (e.g. ParentID), so any depth needs repeated joins / recursive queries
- **Object-relational (impedance) Mismatch**: objects can contain far more complex relationships, relational databases store data as flat tables of rows and columns. Objects have nesting, lists, inheritance; tables are flat rows → extra mapping code (ORM)
- **Unstructured data handling**: what about text, images and videos? They don't fit fixed columns; stored as BLOBs that can't be meaningfully queried
