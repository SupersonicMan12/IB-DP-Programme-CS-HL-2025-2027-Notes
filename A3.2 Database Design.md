 ### A3.2.1 Describe database schemas.
- Conceptual schema, logical schema, physical schema 
- Abstract definitions of the data structure and organization of the data at different levels 

Database Schema = blueprint defining structure, organization and constraints, guiding the design and implementation

**Conceptual Schema**: abstracts to:
- Entities
- Relationships between Entities
- No attributes or constraints
- ERD Entity-Relationship Diagrams, further discuss in 3.2.2

**Logical Schema**: more detail to conceptual schema: 
- attributes for each entity
- identifies primary and foreign keys to establish relationships

**Physical Schema**: considers how the data will be stored in DB:
- Storage details: **data types** for each attribute
- Indexes, files, storage structures. 
- Implementation-specific.

> [!ai-fix] AI Fix — significance of ERDs (syllabus A3.2.2)
> - **Blueprint**: design the structure before any tables or code are written
> - **Communication**: non-technical stakeholders can verify the design early
> - **Reveals relationships**, especially M:N ones that need junction tables
> - **Catches design errors** (missing entities, wrong cardinality) before implementation, when they are cheap to fix
> - **Bridge**: conceptual schema → logical/physical schema, and ongoing documentation for maintenance

Components:
- Entities have Attributes
- Relationships: connections between entities, diamonds or lines
- Cardinality: recall 1:1, 1:N, M:N
- Modality (often not shown): mandatory / optional

> [!ai-fix] AI Fix — modality + notation key (syllabus A3.2.2)
> **Modality** = whether an entity's participation in a relationship is optional or mandatory.
> - Mandatory: every record must take part (e.g. every Activity must have a Teacher → `TeacherID` cannot be NULL)
> - Optional: a record may take part zero times (e.g. a Student may join no clubs → no signup record exists)
> - Why it matters: modality decides whether a foreign key can be NULL, so it directly affects data integrity.
>
> Notation key (crow's foot, as in the figure below):
> - Rectangle = entity, diamond/line = relationship, oval = attribute
> - `1`, `N`, `M` = cardinality (how many records on each side)
> - `|` = mandatory (at least/exactly one), `o` = optional (zero allowed), crow's foot `<` = many

## A3.2.5 Explain the difference between normal forms.
- First normal form (1NF), second normal form (2NF), third normal form (3NF) 
- The terms atomicity, unique identification, functional dependencies, partial-key dependencies, non- key/transitive dependencies 
- Normalization issues can encompass data duplication, missing data, and a range of dependency concerns, including data dependencies, composite key dependencies, transitive dependencies, and multi-valued dependencies. 

Gradually improve:
Unnormalized Form.
1NF: data is atomic and each table has a unique identifier
2NF: eliminates **partial key dependencies** by ensuring that all non-key attributes depend on the **entire primary key**
3NF: removes **transitive dependencies**, so that non-key attributes depend on the **primary key**.

***Dependency*** = "THIS DECIDES THAT" RELATIONSHIP: if i know "StudentID = 001", i know "StudentName = Hans", StudentID determines StudentName. Usually, we say that the primary key **determines** other attributes. 

> [!ai-fix] AI Fix — missing syllabus terms (A3.2.5)
> - **Data dependency**: the umbrella term — any case where one attribute determines another. Functional, partial-key, transitive and multi-valued dependencies are all data dependencies.
> - **Composite key dependency**: a dependency on a composite key. Problems arise when a non-key attribute depends on only *part* of it (that is a partial-key dependency) — see the Signup example below.
> - **Non-key dependency**: a dependency between two non-key attributes, where neither is the primary key (e.g. `TeacherName → TeacherEmail`). These are exactly the transitive dependencies that 3NF removes.

## A3.2.6 Construct a database normalized to 3NF for a range of real-world scenarios. 
- Examples may include library management, hospital management, e-commerce platforms, school management, employee management, inventory management, police crime reporting 

This is great for practice, scenarios:
- **School Clubs**: a school keeps one large spreadsheet for club sign-ups. Each row records one student, using a student code, the student’s full name, grade level, homeroom teacher, homeroom teacher email, and payment status for activity fees. In the same row, the school also stores all clubs the student joined: each club has a club code, club title, meeting day, room number, supervisor name, and supervisor email. A student may join several clubs, so the club codes, club titles, meeting days, room numbers, supervisor names, and supervisor emails are written as repeated lists inside the same row. The same club can appear in many students’ rows, and the same supervisor may supervise several clubs.
- **Online Store**: An online store keeps all customer purchases in one table. Each row stores an order number, order date, customer number, customer name, customer phone number, customer city, delivery address, and payment method. In the same row, the store stores all items bought in that order: each item has a product code, product name, category name, supplier name, supplier email, quantity bought, and unit price. One order may contain several products, so product codes, product names, categories, suppliers, quantities, and prices are written as repeated values in the same row. The same customer may place many orders, the same product may appear in many orders, and the same supplier may supply many products.

> - **Library Management**: A library keeps all loans in one table. Each row stores a project code, project name, project budget, and all employees assigned: for each employee, the employee number, employee name, job title, hourly rate, department name, and department manager. One employee may work on many projects, one project has many employees, and each employee belongs to one department.
> - **Inventory Management**: A warehouse keeps stock in one table. Each row stores a product code, product name, and all warehouses storing it: for each warehouse, the warehouse code, city, manager name, quantity on hand, and reorder level. The same product is stored in many warehouses, one warehouse stores many products, and each warehouse has one manager.
> - **Police Crime Reporting**: A police force keeps crime reports in one table. Each row stores a report number, report date, reporting officer name, reporting officer badge number, and all suspects named in the report: for each suspect, the suspect ID, name, address, offence code, offence description, and offence severity. One report may name several suspects, one suspect may appear in many reports, and one officer files many reports.
>
> **Model answer (Library Management, 3NF):**
> - `Member(MemberNo, MemberName, MemberPhone)`
> - `Author(AuthorID, AuthorName, AuthorNationality)`
> - `Publisher(PublisherID, PublisherName, PublisherAddress)`
> - `Book(ISBN, Title, AuthorID, PublisherID)`
> - `Loan(MemberNo, ISBN, LoanDate, DueDate)`, PK `(MemberNo, ISBN, LoanDate)`
>
> Where the dependencies go: `MemberNo → MemberName, MemberPhone` and `ISBN → Title, AuthorID, PublisherID` are partial-key dependencies on the composite key `(MemberNo, ISBN, LoanDate)`, so they are split out in 2NF; `AuthorName → AuthorNationality` and `PublisherName → PublisherAddress` are transitive dependencies, so they are split out in 3NF. `Loan` keeps the composite key and has no non-key attributes left to violate 3NF.

## A3.2.7 Evaluate the need for denormalizing databases. 
- The advantages and disadvantages of normalizing and denormalizing databases 
- Situations where denormalization can enhance performance, particularly in read-intensive applications 
- The balance between straightforward query structures and the risk of data redundancy in denormalized schemas

Normalization:
Advantage:
- less data duplication
- fewer update errors and easier to maintain
- better data integrity
Disadvantage:
- more tables
- more joints
- queries become slower and more complex as it navigates through tables

Denormalization:
Advantage:
- simpler queries
- useful for reports, dashboards and scenarios requiring humans to read / **read-intensive** applications
Disadvantage:
 - data redundancy
 - high storage use
 - greater risk of inconsistency when updating

ALWAYS SAY READ-INTENSIVE!!

A balance point between the two must be found. Yes, balance.

> [!ai-fix] AI Fix — evaluating denormalization (A3.2.7)
> **Situations where denormalization pays off:**
> - Read-intensive systems (dashboards, reports, analytics) where reads far outnumber writes
> - Queries that need many joins across large tables — storing a pre-joined, redundant copy avoids the joins
> - Precomputed aggregates (totals, counts, averages) stored instead of recalculated on every query
> - Data warehouses, OLAP and star schemas, where data is historical and queried rather than updated (links to A3.4)
> - Caching frequently requested data
>
> **Managing the risk:**
> - Triggers or scheduled sync jobs keep duplicated data consistent
> - Treat the denormalized copy as read-only, with the normalized tables as the single source of truth
>
> **Judgment (the "evaluate" part):** the right answer depends on the read:write ratio and how critical consistency is. Write-heavy, integrity-critical systems should stay normalized; read-heavy reporting systems should denormalize selectively, trading storage and update risk for speed. Denormalization is a deliberate trade-off, not an upgrade — use it only where measured performance justifies it.
